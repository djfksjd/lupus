A1–A5는 수용한다. A3의 재귀 해시는 파일 내용뿐 아니라 상대 경로·추가·삭제·심볼릭 링크 처리도 포함해야 한다.

**B1 — 조건부 동의: 좁은 복구 MVP에는 가능하지만, 변경 주체 판정은 반대한다.**  
실행 전후 hash 차이만으로 worker 변경이라고 단정할 수 없다. 실행 중 사람이 편집했다면 자동 복원이 그 변경을 지운다.  
새 `conftest.py` 같은 탐색 파일, 미고정 의존성·실행 환경, 제품 코드의 검사 우회, 같은 권한으로 runtime 수정은 놓친다.  
**이 조건이면 동의:** 사람의 동시 편집을 금지한 범위로 한정하고, 출처가 불명확한 변경은 보존하고 NEEDS_ANSWER로 중단한다.  
pin은 crash 후에도 유지하고 검사 전후 확인한다. 보호 위반은 복원 후 PASS여도 해당 시도를 실패 처리하며, 테스트 수·식별자·skip도 확인한다.

**B2 — 방향에는 동의, 이번 실패 테스트 복구 MVP에서는 제외한다.**  
red는 현재 구현과 구별된다는 증거이지 요청을 충분히 검증한다는 증거는 아니다. 승인에도 검토 시간이 든다.  
**이 조건이면 후속 실험에 동의:** 테스트 작성 단계에서 제품 코드·기존 검사를 바꾸지 못하고, 원래 구현에서 요구 동작의 assertion 실패로 red를 확인한다.  
사람에게 요청별 검사 대응·누락과 테스트 diff를 보여 승인받고, 승인한 정확한 버전을 고정한다.  
재시도 중 검사 완화는 재승인 대상으로 삼고, 고정 검사·기존 회귀·실제 수집 여부를 함께 판정한다.

**B3 — 사전 검증에는 동의, 묶음은 아직 실행 계약이 부족하다.**  
claim 이후 직접 검증하는 제한은 타당하다. 호출 없는 DONE도 새 증거·검증 비용·checkpoint를 남겨야 한다.  
뒤 작업 지시를 앞 prompt에 넣으면 뒤 작업의 실제 변경은 자기 checkpoint보다 먼저 일어난다. 작업별 기록만 유지한다고 이 경계가 보존되지는 않는다.  
**이 조건이면 동의:** 호출 전에 포함 작업·revision·허용 변경·의존 순서·공유 예산을 명시하고, 중단 시 포함 작업 전체를 재검증 대상으로 기록한다.  
뒤 작업의 변경이 앞 작업을 깨뜨릴 수 있으므로 최종적으로 앞 조건도 재검증한다. 이것이 내가 말한 명시적 실행 단위다.

**B4 — 대체로 동의, 두 가지 보완이 필요하다.**  
(i)에 B1의 동시 편집·보호 위반·crash 복구 검증을 포함해야 평가의 PASS를 믿을 수 있다.  
(ii)는 일반 작업뿐 아니라 중단·Claude↔Codex 인계를 포함하고, 직접 CLI의 native resume/인계 기준선과 비교해야 한다.  
묶음은 A5만으로 채택하지 말고 별도의 묶음 대 비묶음 비교를 요구한다.  
**이 조건이면 순서에 동의:** (iii)는 검증된 선택지만 결정하고, 묶음 근거가 부족하면 보류한 채 (iv)로 진행한다.

**B5 — 목표와 잘못된 완료율의 1급 지표화에 동의한다.**  
가장 약한 고리는 **인계 후 PASS 증거의 유효성을 판단하는 입력 범위**다.  
현재 코드는 선언한 경로 밖의 수동 변경을 탐지하지 못한다고 명시한다. 재귀 해시는 선언 경로 내부만 개선한다. [goals.py](lupus/src/lupus/goals.py:462)  
따라서 검사 입력 범위를 충분히 묶거나, 재개 시 새 검증을 의무화해야 “완료 신뢰도를 유지하는 인계”를 주장할 근거가 생긴다.
