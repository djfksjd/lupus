# Lupus 1.6 — 구현 전 타당성 검토와 첫 구현 기록

검토·구현일: 2026-10-05. 대상: [전체 설계](LUPUS-PLAN.md) 1.5와 부속 검수 문서 7종. 작성자(Claude Opus 5.5)의 검토와 Codex CLI 0.160.0(`codex exec`, 읽기 전용)의 독립 검토를 합쳤다. 이전 검수는 문서 일관성을 봤고, 이번에는 **구현자가 막히거나 잘못 만들 지점**을 봤다. 이번에는 실제 코드와 실행 시험이 있다: [lupus/](../../lupus/), 기계 계약은 [lupus/docs/CONTRACT.md](../../lupus/docs/CONTRACT.md).

## 판정

설계 방향은 타당하다. 단일 supervisor, 운영 DB와 기억의 분리, 객체→DB commit 순서, 증거 기반 완료, 미검증을 미검증으로 두는 보고 원칙은 그대로 구현할 수 있었다. 다만 1.5는 정책 계약이지 구현 명세가 아니었고, 아래 9건은 구현 전에 결정이 필요했다. 모두 1.6에서 결정해 코드와 시험으로 고정했다.

## 아직 입증되지 않은 것

- **기본 CLI 대비 이득(§23).** 비교 실험을 하지 않았다. 현재 확인된 것은 기능이 동작한다는 사실뿐이며 비용 절감이나 우월성은 주장할 수 없다.
- **보안 격리.** worker는 사용자와 같은 권한으로 실행된다. 보호 업무, 민감정보 무유출, 인증 저장소 분리는 지원하지 않는다.
- **자동 활성화.** 평소 `claude`/`codex` 실행에 연결되지 않는다. 지금은 `lupus run`으로 명시 실행한다.
- **전원 장애 내구성.** 프로세스 강제 종료만 시험했다.
- **신뢰도.** 실제 CLI 호출은 경로당 1~3회 성공이다.
- **quota 감지.** 제공자 한도 오류는 메시지 문자열로 분류한다. 실제 한도 소진 상황에서 확인하지 못했다.
- **기본 입력 비용.** 설정을 차단한 한 줄짜리 요청에서도 관측된 입력은 Claude 약 1만 토큰, Codex 약 3.5만 토큰(대부분 캐시)이었다. 각 1~2회 관측이며, Lupus가 붙이는 prompt는 수백 자 수준이지만 호스트 자체의 고정 비용은 줄이지 못한다.
- **증거의 유효 범위.** 선언하지 않은 파일을 run 없이 사람이 직접 고친 경우는 감지하지 못한다.

## 다음 단계 제안

1. 실제 작은 업무 3~5개로 기본 CLI / Lupus-off / Lupus-on을 비교해 §23의 채택 계약(비용 효율 또는 기능 편익)을 먼저 판정한다. 이득이 없으면 범위를 늘리지 않는다.
2. 이득이 확인된 기능에 한해 자동 활성화(런처·훅)를 임시 설치 → 되돌림 시험 순으로 붙인다.
3. 보호 업무가 실제로 필요해질 때 격리 실행 경계를 검토한다. 그 전에는 보호 모드를 표시하지 않는다.

사용자 결정이 필요한 항목: 기존 Obsidian Vault 연결 여부, 프로젝트별 허용 제공자, 업무별 기본 예산.

3차에서 Codex는 2차의 10건이 더는 재현되지 않음을 확인했다. 3차의 3건은 수정했지만 **그 수정에 대한 Codex의 재확인은 받지 않았다.** 리뷰가 차수마다 새 결함을 찾았으므로 남은 결함이 없다고 볼 근거는 없다. 작성자 자체 검토로 추가한 것: runtime당 supervisor 하나(flock), 증명할 수 없는 프로세스 그룹에는 신호를 보내지 않음, CLI 버전이 측정 시점과 다르면 native 실행 거부, CLI 부재를 환경 대기로 분류, zombie를 살아 있는 writer로 보지 않음.

리뷰가 반복해서 드러낸 설계상의 교훈은 계획에도 해당한다: (1) 프로젝트 안에서 코드를 실행하는 것은 worker만이 아니며 검증기도 writer로 취급해야 한다. (2) "재개 가능" 판정은 그 판정에 근거한 행동과 같은 트랜잭션이어야 한다. (3) 증거에는 '무엇을 언제 검사했는가'가 함께 묶여야 하며 재연결·계약 변경이 그것을 새것으로 만들면 안 된다.

## 1.7 — 기억 그래프, 전용 Vault, 그래프 보기, 첫 비교 실험 (2026-10-05)

사용자 결정: 전용 Vault를 둔다. Obsidian은 "노드를 이어 지식 구조를 만든다"는 방식만 참고하고 그대로 쓰지 않으며, Lupus 고유의 방식을 만든다. 그래프 화면은 사용자가 조사한 목록 밖의 GitHub 오픈소스를 수정 없이 가져와 쓴다.

### 만든 것

- **기억 그래프** (`memory.py`, migration 0002): 종류·상태·출처를 가진 노드와 종류가 있는 연결. 프로젝트 범위 격리, 한국어 2글자 토큰 검색, 토큰 한도 안의 회상, 시도 결과의 피드백, 자동 승격·은퇴, 삭제와 재등록 차단. 규칙은 CONTRACT "기억 그래프".
- **실행 루프 연결**: 시도 시작 시 회상해 prompt 끝에 참고 자료로 붙이고, 검증 결과를 노드에 되돌리며, 검증을 통과한 시도의 `LESSON:` 줄과 무진전 기록을 노드로 남긴다. 모델 호출을 추가하지 않는다.
- **전용 Vault** (`vault.py` 재작성): `<home>/vault`. 노드당 문서 하나와 상대 링크, 지도, 목표 현황. 이전의 Obsidian 폴더 구조는 없앴다.
- **그래프 보기** (`graph.py`, `viewer/`): `lupus graph`. vis-network 10.1.2(visjs, Apache-2.0/MIT)의 독립 번들을 **수정 없이** 포함. npm 무결성 해시를 확인해 `upstream-lock.json`에 고정했고, 파일이 바뀌면 시험이 실패한다. 헤드리스 Chrome에서 렌더링을 한 번 확인했다.
- **스키마 migration**: 번호 붙은 SQL 파일, 적용분 checksum, 이전 버전 DB는 백업 후 자동 승급.

시험은 오프라인 164개로 늘었고 모두 통과한다.

### Codex 리뷰 (4차, 새 코드만)

5건(P1 1, P2 4): Vault가 자기가 쓰지 않은 기존 파일을 덮어씀 · symlink 검사 전에 폴더를 만듦 · 뷰어 스크립트 복사가 symlink를 따라 씀 · worker 문장이 Vault 문서에서 외부 이미지·링크가 됨 · 회상 한도가 머리말과 라벨을 세지 않음. 모두 수정하고 재현 시험을 추가했다. 이 수정분에 대한 재확인은 받지 않았다.

**한계:** 칸마다 1회 실행이라 비율이나 유의성을 말할 수 없다. 작업 3종은 모두 한 번에 끝나는 쉬운 작업이다. Lupus가 이득을 낼 것으로 설계된 상황(중단 후 재개, AI 교체, 여러 단계 업무, 반복되는 프로젝트 지식)은 기능 시험만 했고 기본 CLI와 비용을 비교하지 않았다. 따라서 §23의 채택 계약 중 **비용 효율은 입증되지 않았고**, 기능 편익(복구·인계·기억 전달)은 동작만 확인된 상태다.

### 다음 판단

단순 작업에는 Lupus를 쓰지 않는 것이 현재 자료에 맞다. 다음 비교는 실제로 겪는 여러 단계 업무 2~3개에서 중단·재개와 프로젝트 지식 재사용을 포함해, 사람이 다시 설명하는 비용까지 재는 것이 의미 있다. 그 결과가 나오기 전에는 자동 활성화 설치로 넘어가지 않는다.

## 1.8 — 단순 작업에서도 이득이 나게 하기, 그리고 측정 (2026-10-05)

사용자 요구: 비교할 업무는 직접 고르고 효과를 입증할 것. 단순 작업조차 기본 CLI보다 이득이 있을 것.

### 무엇을 바꿨나

1.7의 pilot은 "설정을 끈 CLI"와 비교했고 Lupus가 약간 손해였다. 그 비교에는 두 가지가 빠져 있었다. 사용자가 실제로 쓰는 CLI는 설정을 끈 CLI가 아니라 플러그인·훅·MCP·스킬이 모두 붙은 CLI이고, Lupus는 검증을 직접 하면서도 worker에게 평소처럼 스스로 읽고 확인하게 두고 있었다. 그래서 경량 실행 경로를 넣었다(규칙은 CONTRACT "경량 실행 경로").

- **작업 파일 동봉**: 검증기가 보는 파일을 prompt에 넣어 모델의 파일 읽기 왕복을 없앤다.
- **한 번에 쓰기**: 검증은 supervisor가 하므로 worker의 자체 테스트·재확인을 생략시킨다.
- **교훈 요청은 실패 뒤에만.**
- **가벼운 설정 먼저(선택)**: 검증이 있으니 가벼운 모델을 먼저 써 보고, 실패하면 기본 모델.

### 비교 조건

| 조건 | 내용 |
|---|---|
| A0 평소 CLI | 사용자의 현재 설정 그대로(`claude -p`, `codex exec`). 플러그인 28개, 훅, MCP, 스킬 포함 |
| A 설정 끈 CLI | Lupus와 같은 실행 플래그, Lupus 없음. 사람이 직접 치는 것과 같은 prompt |
| C Lupus | 경량 실행 경로 전체 |

같은 작업, 같은 검증기, 실행마다 새 디렉터리. 원자료: `lupus/docs/compare-simple-2026-10-05.json`, `compare-project-2026-10-05.json`. 스크립트: `lupus/evaluations/compare.py`.

### 이 결과로 말할 수 있는 것과 없는 것

- 말할 수 있는 것: 이 Mac, 이 CLI 버전, 이 작업들에서 Lupus는 단순 작업과 여러 단계 업무 모두에서 사용자의 평소 CLI보다 토큰과 시간을 뚜렷하게 덜 썼고 결과 품질(검증 통과)은 같았다. §23의 **비용 효율 계약은 이 범위에서 충족**했다.
- 반복 수가 작다(칸당 1~2회). 방향과 크기는 일관되지만 비율을 정밀한 값으로 읽으면 안 된다. Codex는 실행마다 캐시 적중 차이가 크다.
- 가장 큰 몫은 "설정을 싣지 않는 것"이다. 플러그인·MCP·스킬이 실제로 필요한 작업은 이 경로로 못 하므로, 그런 작업에는 이 절감이 적용되지 않는다.
- "한 번에 쓰기"는 여기서 실패를 만들지 않았지만(Lupus의 시도 36회 중 재시도 0회) 작업이 어렵거나 검증기가 느슨하면 재시도나 틀린 통과가 생길 수 있다. 더 어려운 작업에서의 통과율은 측정하지 않았다.
- 사용자가 평소 CLI의 플러그인을 직접 정리하면 A0와 A의 차이는 Lupus 없이도 줄일 수 있다. 그 경우에도 A 대비 이득(Claude 토큰 −32%, Codex −48%)은 남는다.
- 구독 한도에서 실제로 얼마가 덜 차감되는지는 관측할 수 없다.

경량 실행 경로 코드는 Codex 리뷰를 받지 않았다. 오프라인 시험은 173개 통과.

## 1.9 — Codex와의 방향 토론, 거짓 완료 방지, 한 줄 실행, holdout 측정 (2026-10-05)

### 토론 결과

Codex에게 반대 입장과 오픈소스 비교를 맡겨 두 차례 토론했다.

| 다른 모델의 판정 | 기계 검사가 안 되는 조건의 검증기로 | 확률적 판단을 결정적 증거처럼 쓰면 안 된다 | 이번에는 하지 않음 |
| 호출 묶음 | 뒤 작업 지시를 앞 호출에 포함 | 작업별 checkpoint 경계가 깨진다. 명시적 실행 단위와 별도 비교 필요 | 보류. "이미 충족된 작업 건너뛰기"만 구현 |
| 절감의 공로 | Lupus의 이득 | supervisor 없이 같은 prompt 기법만 쓴 기준선이 필요 | 수용, 측정함(아래) |
| 사람 수고 | 인계 설명 0자 | 목표·검증기 작성 수고를 세지 않았다 | 수용, 계상함(아래) |
| "모든 오픈소스보다 낫다" | — | 서로 다른 문제를 푸는 제품을 한 줄로 세울 수 없다 | 목표를 좁힘 |

**좁힌 목표:** 검증 가능한 작업을 Claude↔Codex로 중단·재개할 때, 완료 신뢰도를 유지하면서 재설명 시간과 총 실행 비용을 줄인다. 잘못된 완료율을 1급 지표로 둔다.

Codex가 조사한 오픈소스 비교의 요지(출처는 토론 기록): 대화형 편집(aider), 격리 실행 플랫폼(OpenHands), 평가 기반(SWE-agent), 요구→계획 흐름(Task Master, spec-kit, BMAD), 평소 CLI 안에서의 절차(superpowers), 팀 실행과 훅 통합(Ruflo, oh-my-claudecode), worktree 세션 관리(claude-squad 등), 의미 검색 기억(mem0, Letta, Graphiti)은 Lupus보다 앞서 있다. 자동 테스트 되먹임과 checkpoint는 Lupus만의 것이 아니다. Lupus가 상대적으로 드문 것은 **설치된 Claude/Codex를 바꿔도 목표·예산·시도·증거 revision을 하나의 로컬 원장으로 이어가고, 완료를 모델의 선언이 아니라 고정된 검사의 관측으로만 결정하는 좁고 강한 계약**이다.

### 구현

- **검증 수단의 보호** (`protect.py`): 테스트·설정을 고정하고, worker가 바꾼 것은 검증 전에 되돌린다. 테스트 0개 실행은 통과가 아니다.
- **`lupus fix-tests`** (`quick.py`): 목표 파일 없이 한 줄. supervisor가 먼저 실패를 관측해야 목표가 생긴다.
- **재시도 품질**: 실패한 검증기의 실제 출력을 전달하고 두 번째 시도는 자체 확인을 허용.
- **이미 충족된 작업 건너뛰기**: 중단 뒤 재개 시 디스크에 이미 있는 작업을 검증만 하고 다시 호출하지 않는다.
- 구현 중 발견한 결함: 같은 초에 같은 길이로 고쳐진 파이썬 파일을 검증기가 낡은 bytecode로 판정할 수 있었다. 디렉터리를 증거 범위로 선언하면 내용이 바뀌어도 hash가 같았다(Codex 지적). 둘 다 수정.

### 측정 1 — 절감의 공로는 누구에게 있나 (holdout 포함)

숨긴 검사가 있는 더 어려운 작업 3종(구간 병합·빈 시간, 기간 문자열 파서, TTL-LRU 캐시), CLI당 조건별 6회, 순서 무작위. worker는 보이는 테스트만 받고, 더 엄격한 holdout 테스트는 결과물의 사본에서 사후 실행한다. 원자료: `lupus/docs/bench-*-2026-10-05.json`.

| CLI | 조건 | holdout 통과 | 토큰 | 시간 | 사람 입력 |
|---|---|---|---|---|---|
| Claude | A 설정 끈 CLI, 평범한 prompt | 6/6 | 20,134 | 18.6초 | 418자 |
| Claude | A+ 같은 CLI + Lupus의 prompt 기법만 | 6/6 | 13,314 | 10.0초 | 418자 |
| Claude | C Lupus | 6/6 | 13,320 | 9.3초 | 777자 |
| Codex | A | 6/6 | 76,723 | 33.6초 | 418자 |
| Codex | A+ | 6/6 | 37,037 | 21.4초 | 418자 |
| Codex | C | 6/6 | 37,035 | 20.3초 | 777자 |

- **한 번에 끝나는 작업에서 토큰 절감의 공로는 supervisor가 아니라 prompt 기법(파일 동봉 + 한 번에 쓰기)에 있다.** A+와 C가 같다. 1.8에서 "Lupus의 이득"이라고 쓴 A→C 구간은 정확히는 이 기법의 이득이다.
- supervisor는 토큰을 더 쓰지 않는다(C = A+). 대신 목표를 정의하는 **사람 입력이 약 1.9배**다.
- 36회 전부 holdout을 통과했고 **잘못된 통과는 0건**이었다. "한 번에 쓰기"가 정확도를 떨어뜨린다는 증거는 없어 기본값으로 유지한다. 다만 이 작업들이 실패를 유도할 만큼 어렵지 않았다는 뜻이기도 하다. 보호 파일이 잘못된 통과를 줄이는지는 이 벤치마크로 보이지 못했다(오프라인 시험에서 조작 시나리오로만 확인).

### 측정 2 — 한 줄 실행 (`fix-tests`)

버그가 있는 `inventory.py`와 실패하는 테스트가 있는 폴더에서 각 1회. 원자료: `lupus/docs/fix-tests-2026-10-05.json`.

| CLI | 사람 입력 | 토큰 | 시간(사전 테스트 실행 포함) | 결과 |

### 냉정한 결론 갱신

- 한 번에 끝나는 일반 작업: Lupus의 가치는 비용이 아니라 **검증된 완료**다. 비용 절감은 prompt 기법만으로도 얻는다.
- 실패 테스트 복구: 한 줄로 실행되고 비용·시간·사람 입력이 모두 줄어든다. 지금 Lupus를 쓰는 편이 나은 경우다.
- 여러 단계·중단·AI 교체: 1.8의 측정대로 합계는 줄지만 Codex처럼 호출당 고정 입력이 큰 CLI에서 작업을 나누면 손해다(묶음은 미구현).
- 기계로 검사할 수 없는 작업, 대화형 작업, 플러그인이 필요한 작업: 여전히 기본 CLI가 낫다.

### Codex 리뷰 (5차, 토론 이후 코드)

### 1.10 보완 — Codex 읽기 차단 해결, Codex 리뷰 6차

- **Codex 읽기 차단을 해결했다.** `--sandbox workspace-write` 대신 권한 프로필(`default_permissions` + `permissions.<이름>.filesystem`)을 쓴다. 읽기는 `:minimal`·Codex 프로그램·도구 체인, 쓰기는 프로젝트와 임시 폴더뿐이다. 홈 디렉터리 canary: 기본 sandbox에서는 읽힘 → 프로필에서는 `BLOCKED`. 같은 프로필에서 worker 명령의 `curl`은 실패했다(네트워크 없음). 실제 Claude↔Codex 인계 시험 3개도 이 프로필로 통과했다. 각 1회 측정이다.

## 1.11 — 일반 요청 한 줄 실행 `lupus do` (2026-10-05)

토론에서 후속 과제로 합의한 red-first 방식을 구현했다. 규칙은 CONTRACT "일반 요청 한 줄 실행". 목적은 사람이 검증기를 **쓰지 않고 읽고 승인만** 하게 하면서 "worker의 자기 보고는 증거가 아니다"를 지키는 것이다.

실측(`lupus/evaluations/request.py`, `lupus/docs/request-2026-10-05.json`): 기존 모듈에 함수 하나를 추가하는 요청, CLI당 각 1회, 승인은 자동으로 대체, 채점은 worker가 보지 못한 holdout 테스트.

| CLI | 조건 | holdout | 호출 | 토큰 | 시간 | 정가 추정 |
|---|---|---|---|---|---|---|
| Claude | 평범한 CLI 호출(설정 끔) | 통과 | 1 | 17,065 | 9.2초 | $0.046 |
| Claude | `lupus do` | 통과 | 2 | 28,053 | 17.0초 | $0.089 |
| Codex | 평범한 CLI 호출(설정 끔) | 통과 | 1 | 72,123 | 31.6초 | — |
| Codex | `lupus do` | 통과 | 2 | 74,066 | 47.0초 | — |

- 양쪽 CLI에서 끝까지 동작했다: 검사 초안이 실패 상태로 확인됐고, 구현 뒤 승인된 검사와 기존 테스트가 통과했으며 holdout도 통과했다.
- **토큰은 평범한 호출의 약 1.0~1.6배(Claude 정가 추정은 약 2배), 시간은 약 1.5~1.8배다.** 이 작업에서는 평범한 호출도 holdout을 통과했으므로 품질 이득은 보이지 않았다. `lupus do`가 주는 것은 더 싼 결과나 더 좋은 결과가 아니라, 사람이 승인한 검사로 확인된 완료와 기존 테스트의 회귀 차단이다. 작은 일회성 요청에는 과하다.
- 사람은 요청 한 줄을 쓰고, 생성된 테스트(이 측정에서 47~55줄)를 읽고 승인한다. 읽는 시간은 측정하지 않았다.
- 위 표는 아래 리뷰 수정(진짜 실패만 인정 등)을 반영한 뒤 다시 측정한 값이다.

### Codex 리뷰 (7차, `lupus do`)

## 1.14 — `lupus do` 비용 절감과 전체 점검 (2026-10-07)

### `lupus do`를 한 번의 호출로

1.13에서 "해결하지 못했다"고 적은 항목이다. 비용의 원인은 호출이 두 번(테스트 작성, 구현)이라는 것이었다. 테스트와 구현안을 한 호출에서 받되 구현안은 `.lupus-staged/`에 따로 두고, 테스트 확인·표시·승인은 지금의 코드로 한 뒤, 승인되면 구현안을 옮겨 고정된 테스트로 검증하도록 바꿨다. 통과하면 두 번째 호출이 없다.

| 3회 평균, holdout 모두 통과 | 평범한 호출 | 예전 `do` (2회 호출) | 지금 `do` (1회 호출) |
|---|---|---|---|
| Claude | 17,493 토큰 · 10.1초 | 29,104 · 18.0초 | 15,629 · 15.1초 |
| Codex | 72,083 토큰 · 24.4초 | 74,245 · 34.6초 | 37,502 · 24.8초 |

남은 점: Claude에서는 평범한 호출보다 5초 느리고, 출력 토큰 비중이 커서 CLI가 보고한 정가 환산 추정액은 0.077달러 대 0.048달러로 더 높다. 구현안이 틀리면 평소의 구현 시도가 한 번 더 든다(이 측정에서는 3회 모두 첫 구현안이 통과). 작업 하나, 3회 측정이다.

### 전체 점검

보안·잘못된 완료 이외의 문제를 찾기 위해 저장소 전체를 Codex에 점검시켰고(16건), 실제 터미널에서 실제 Claude로 `fix-tests`와 `do`를 처음부터 끝까지 실행해 보았다.

- 막힌 뒤 빠져나올 명령이 없던 것: `resolve`의 메모가 다음 시도에 전달되지 않고 같은 시도로 거부됨 · 문서 승인을 미루면 다시 승인할 방법이 없음 · 권한 철회 뒤 재확인 명령이 CLI에 없음 · 한도로 멈춘 목표를 `run`이 다시 시도하지 않음 · `refreeze` 뒤에도 작업이 대기에 머묾.
- 남는 것: `do` 중 Ctrl-C에 테스트 초안이 남음 · 거부된 명령이 등록한 폴더가 남아 상위 폴더 등록을 막음 · runtime의 보관 파일이 계속 쌓임.
- 잘못된 대상: 하위 폴더에서 실행하면 하위 폴더를 등록 · `write --out`이 현재 위치가 아니라 프로젝트 최상위 기준.
- 입력: 잘못된 goal 파일이 traceback으로 끝남 · 설정 파일 없는 pytest 프로젝트를 unittest로 실행 · `package.json` 스크립트의 옵션을 버림 · 컨테이너 모드가 호스트 도구를 요구하고 `PYTHONPATH`를 버림 · cargo의 `target/`이 감시 한도를 넘김 · Rust 기준 실행을 두 번 함.
- 직접 써 보고 고친 것: 결과가 수백 줄의 JSON으로만 나옴(터미널에서는 몇 줄 요약, `--json`으로 전체).

16건 모두 수정했다.

## 1.15 — "대체 가능한 수준"을 향한 작업과 그 결과 (2026-10-07)

사용자의 요청은 Aider·OpenHands 등을 대체할 수 있는 수준으로 올리는 것이었다. Codex와 우선순위를 토론했고(반대 의견 포함), 그 결론과 측정 결과를 그대로 적는다.

### Codex의 반대 의견과 반영

내 계획은 품질 벤치마크 → 큰 저장소 대응 → git 통합(자동 커밋·undo) → 병렬 실행이었다. Codex의 반대: (1) 벤치마크는 순위표가 아니라 작은 진단 파일럿으로, 잘못된 DONE 비율을 보고할 것 (2) 검색 도구만으로는 부족하고 "한 번에 쓰기" 강제를 풀 것 (3) 자동 커밋보다 격리가 먼저: 커밋된 HEAD의 별도 체크아웃, diff, 버리기, 명시적 수락 (4) 병렬은 미룰 것 (5) 빠진 것: 저장소의 실제 환경 존중, 생성된 검사의 수정, 무엇이 확인됐는지 보여 주기 (6) 구조적으로 편집기 통합 도구·자체 에이전트 루프 도구·다중 에이전트 작업 공간을 대체할 수 없으니 그렇게 말할 것. 대부분 받아들였다. 병렬 실행과 자동 커밋·undo는 하지 않았다.

### 구현

| 항목 | 내용 | 확인 |
|---|---|---|
| 격리된 체크아웃 | `--isolated`, `lupus diff / accept / discard` | 시험: 성공·실패·버리기·중단 모두에서 사용자의 파일·index·HEAD가 바이트 단위로 동일. 실제 Claude로 터미널에서 끝까지 실행 |
| `.git` 보호 | OS 수준 쓰기 차단 + 저장·복원 | 측정: 막기 전 Codex는 `.git/hooks`에 쓸 수 있었고, 프로필 수정 뒤에는 못 씀 |
| 저장소 환경 | 프로젝트 가상환경의 인터프리터 사용(지문 고정), 요청과 관련된 소스 우선 | 시험 |
| 탐색 | Glob/Grep 기본 제공, 파일이 다 주어지지 않으면 "찾아 읽고 수정", `--shell` 선택 | 파일럿의 실제 저장소에서 동작 |
| 검사 수정 | 승인 단계의 `edit`, `--allow-failing` | 시험. 파일럿에서 거부되던 4건이 실행됨 |
| 보고 | 확인한 검사 나열, 목표 id와 다음 명령, 진행 표시, 마지막 검증 미실행 사유 | 실제 터미널 실행 |

### 결과 품질 파일럿: 이득이 없었다

`evaluations/issues.py`. 5개 프로젝트의 최근 커밋에서 "커밋의 테스트를 직전 소스에 얹으면 실패하고 커밋에서는 통과"하는 것 20건을 자동으로 골라 검증했다. worker에게는 직전 저장소와 커밋 메시지만 주고 upstream 테스트는 숨겼다.

- Codex 20건: 평범한 호출 13건 통과, `lupus do` 11건 통과. `do`가 시작을 거부한 4건(프로젝트 자체 테스트가 이 환경에서 통과하지 않음)을 빼면 16건에서 11 대 11.
- Claude는 `do`가 건당 평균 6.5분 걸려 7건에서 중단: 7 대 4.
- **Lupus가 DONE이라 한 14건(Codex) 중 5건은 숨긴 테스트를 통과하지 못했다.** 그중 4건은 평범한 호출도 실패한 과제다. 거꾸로 Lupus가 미완료라 한 2건은 실제로는 맞는 구현이었다(스스로 쓴 검사가 틀렸다).
- 토큰은 비슷했고 시간은 `do`가 더 걸렸다(Codex 68초 대 95초).

해석: 같은 모델이 같은 한 줄 요청으로 쓴 검사는 구현과 같은 오해를 담는다. 자동 승인하면 "검사를 통과한 오답"이 나온다. `do`의 가치는 사람이 검사를 읽고 고치는 데 있는데 이 파일럿은 그것을 재지 않았다. 한계: 공개 커밋이라 모델이 기억할 수 있고, 커밋 메시지가 해법을 드러낼 수 있으며, 비교 대상이 Aider 등이 아니라 같은 CLI의 평범한 호출이다.

### Codex 리뷰 (13~14차)

## 1.16 — `lupus do`의 열세 원인 수정과 독립 리뷰 (2026-10-07)

1.15의 파일럿에서 `lupus do`는 평범한 호출에 뒤졌다(Codex 11 대 13, Claude 4 대 7). 요구는 여전히 "대체 가능한 수준"이었다. 이번에는 측정된 원인 하나를 고치고, 1.15의 해석("같은 모델이 쓴 검사는 같은 오해를 담는다")을 겨냥한 기능 하나를 만들어 다시 쟀다.

### 원인: 구현안을 완전한 파일로 쓰게 한 것

Claude의 `do`가 잃은 3건 중 2건은 420초 제한을 두 번 넘긴 것이었다. 1.14의 한 번 호출 방식은 구현안을 `.lupus-staged/`에 완전한 파일로 쓰게 했고, more-itertools의 `more.py`처럼 큰 파일에서는 그것이 편집이 아니라 전체 재작성이 됐다.

제자리 방식으로 바꿨다. worker는 소스를 평소처럼 고친다. supervisor는 초안 목표에서 새 테스트를 뺀 프로젝트 전체를 이미 고정하고 있으므로, worker가 끝나면 그 수정을 되돌리면서 밀려난 판본을 runtime에 보관한다. 그 판본이 구현안이다. 승인 뒤 다시 넣고 고정된 테스트로 먼저 검증한다. 새로 만든 장치는 거의 없고(`protect.restore`가 보관한 경로를 기록하게 한 것, `quick.proposal`) `.lupus-staged/`와 그것을 가리던 샌드박스 규칙·컨테이너 마운트는 없앴다.

실제 CLI로 돌리자 결함 네 개가 더 나왔고, 모두 오프라인 시험이 잡지 못하는 종류였다.

| 결함 | 드러난 방식 | 수정 |
|---|---|---|
| 초안 prompt에 "기존 파일은 수정하지 마라"가 남아 "소스에 직접 구현하라"와 모순 | Codex가 구현을 전혀 하지 않음 | prompt를 다시 씀, 회귀 시험 |
| "구현을 빼 둔다"는 설명을 "지금 고치면 안 된다"로 읽음 | Codex가 소스 대신 `…_implementation.patch` 파일을 만듦 | "패치·사본으로 내지 마라, 되돌리는 것은 Lupus가 한다"고 명시 |
| 테스트 본문이 실행 중 만난 `SyntaxError`를 "테스트 파일이 파싱되지 않는다"로 판정 | 생성된 코드를 exec하는 테스트(sqlparse)가 두 번 거부됨 | 테스트가 로드되어 실행·실패했으면 일반적인 실패로 봄 |
| 재시도 안내에 "소스를 건드려 되돌렸다(수정 금지)" | 한 번 호출 방식에서는 소스 수정이 요청된 일 | 구현안 초안에는 그 안내를 붙이지 않음 |

덧붙여, 초안 이후 사용자가 고친 파일을 구현안이 덮어쓸 수 있었다. 구현안의 파일 중 하나라도 초안 이후 바뀌었으면 구현안 전체를 버린다.

### 독립 리뷰 (`--review`)

검사가 통과한 뒤 구현을 쓰지 않은 모델에게 요청과 diff를 보여 주고 "요청이 말한 동작 중 빠졌거나 다른 것"만 묻는다. 이의마다 요청의 구절을 그대로 인용해야 하고(supervisor가 대조, 없으면 버림), 이의는 같은 완료 조건의 새 목표로 worker에게 한 번 돌려보내며, 그 수정이 승인된 검사를 깨면 되돌린다. 계약은 CONTRACT.md의 "독립 리뷰" 절.

### 재측정

같은 실행에서 평범한 호출과 `do`(+리뷰)를 번갈아 돌렸다. 원자료는 `lupus/docs/issues-*-review-2026-10-07.json`.

| 숨긴 테스트 통과 | 평범한 호출 | `lupus do` |
|---|---|---|
| Codex 20건 | 13 | 13 |
| Claude 12건 | 10 | 11 |

- 제자리 방식의 효과는 분명하다. 850초에 실패하던 Claude의 2건이 54초·100초에 통과한다. 호출 1번으로 끝난 비율은 Codex 16/20, Claude 8/12.
- **열세는 없어졌고 우위는 생기지 않았다.** `do`는 여전히 더 느리다(리뷰 전 기준 Codex 77초 대 55초, Claude 85초 대 46초).
- DONE인데 숨긴 테스트가 실패한 8건 중 7건은 평범한 호출도 실패했다. 커밋 메시지가 upstream 테스트의 기대를 정하지 못하는 과제이고, 이것은 감독으로 고칠 수 있는 문제가 아니다.
- 미완료인데 숨긴 테스트가 통과한 4건은 모두 요청이 기존 테스트가 고정한 동작을 바꾸는 경우다. 고정된 기존 테스트와 요청이 충돌할 때 사용자에게 그 사실을 말하고 선택을 받는 흐름이 없다.
- **독립 리뷰는 효과가 없었다.** 28건 중 이의 2건, 결과를 바꾼 것 0건. 하나는 틀린 구현을 지적했지만 수정 뒤에도 틀렸고, 하나는 upstream 의도와 반대인 지적이었다(수정이 검사를 깨서 되돌려짐). 인용을 요구하고 확신 없으면 말하지 말라고 한 설계가 잡음은 막았지만(버려진 이의 0건, 근거 없는 이의 0건) 잡아낸 것도 없다. 리뷰어가 본 것이 요청 한 줄과 diff뿐이라, worker가 가진 것보다 많은 정보를 갖지 못했다. `--review`는 선택 사항으로 남기고 기본으로 켜지 않는다.

1.15의 해석은 절반만 맞았다. 틀린 결과가 "같은 모델의 같은 오해"에서 나온다면 다른 모델이 잡아야 하는데 잡지 못했다. 이 표본에서 틀린 결과의 대부분은 오해가 아니라 **요청에 정보가 없는 것**이었다.

### Codex 리뷰 (15~17차)

15차 6건: 실행 중인 리뷰의 사본이 `prune`에 지워지면 되돌리기가 "빈 프로젝트"로 읽어 파일을 지움 · 되돌리기용 사본이 큰 파일·바이너리를 빼서 되돌리기가 그 파일을 삭제 · 되돌릴 때 사용자가 그사이 만든 파일을 보관 없이 삭제 · `.env` 같은 파일이 다른 제공자인 리뷰어에게 감 · 리뷰어의 글이 그대로 worker prompt에 들어감 · 두 번째 리뷰를 못 했는데 "남은 이의 없음"으로 보고.
16차 2건: 되돌리기가 실패해도 백업을 지움 · 링크와 의존성 트리의 변경을 못 보고 "되돌렸다"고 함.
17차 2건: 고정되지 않은 `node_modules` 변경을 못 봄 · 남겨 둔 백업이 `prune`의 기간 기준으로 지워짐.

되돌리기를 다시 설계했다: 리뷰어에게 보여 줄 걸러진 사본과, 되돌아갈 완전한 백업(매니페스트를 마지막에 쓰고, 매니페스트가 없으면 거부)을 나눴다. 밀려나는 파일은 모두 runtime에 보관하고, 되돌리지 못한 것이 있으면 완료로 보고하지 않는다. 10건 중 9건을 고쳤다. 17차의 마지막 건(남겨 둔 백업도 `prune --days`의 기간이 지나면 지워짐)은 고치지 않고 보고 문구에 적었다: runtime의 모든 보관 파일이 같은 수명 규칙을 따른다. 17차의 수정분은 재확인받지 않았다. 누적 17회 118건. 오프라인 시험 334개 통과.

### 정직한 위치

"대체 가능한 수준"에는 이르지 못했다. 이번에 얻은 것은 `lupus do`가 평범한 호출보다 결과가 나쁘지 않게 된 것이고, 잃은 것은 "다른 모델이 검토하면 나아질 것"이라는 기대다. Aider·OpenHands와의 직접 비교는 여전히 없다. 남은 것 가운데 측정이 가리키는 순서는 (1) 요청이 기존 테스트와 충돌할 때의 흐름, (2) 요청 자체에 정보가 모자랄 때 구현 전에 사용자에게 되묻는 것, (3) 여러 목표의 병렬 실행, (4) Linux 샌드박스다.

## 1.17 — 세 오픈소스의 동작하는 부분을 옮겨 오기 (2026-10-07)

### 왜 지금

사용자의 처음 지시는 "Ruflo, Ponytail, Prime Agent의 장점 코드를 가져와 Lupus의 계획과 설계 가치에 맞게 변형해 적용하라"였다. 1.16까지의 코드에는 세 프로젝트에서 옮겨 온 코드가 없었다. 설계 검수(LUPUS-REVISION)에서 "최소 안전·재개·메모리 먼저, Ruflo/Prime은 필요와 이득을 확인한 뒤 선택"으로 순서를 바꾼 뒤 그 뒷부분을 하지 않았고, 그 변경을 사용자에게 명시적으로 확인받지 않았다. 사용자가 이를 지적했고, 이번 작업은 그 지시를 이행한 것이다.

### 방법

세 저장소를 스크래치 폴더에 받아(설치·실행 없음, 모두 MIT) 고정 커밋에서 읽었다: Ruflo f1c52f7, Ponytail c982cd4, Prime Agent bc57309. 영역별로 "실제 동작하는 로직 / 외부 패키지 래퍼 / stub·시뮬레이션"을 가렸고, 옮길 후보는 해당 소스를 직접 읽은 뒤 옮겼다. 기준은 둘이다: 원본에서 실제로 동작할 것, Lupus가 이미 가진 것보다 나을 것.

### 원본에서 확인한 것

- **Ruflo**: 실제로 코딩 에이전트를 병렬로 돌리는 경로는 `codex` 패키지의 dual-mode orchestrator와 worktree coordinator 하나다. `swarm`·`claims`는 메모리 안의 장부이고 실행부가 없다(에이전트는 상태 기록, 작업 분해는 고정 템플릿, 합의는 `Math.random() > 0.5`). 통합은 순서대로 `merge --no-ff`를 할 뿐 충돌 복구와 재검증이 없다. 메모리 쪽은 검색 순위(RRF, MMR, coverage floor)와 중복 제거가 의존성 없는 실제 로직이고, 학습 계층(SONA, EWC, ReasoningBank)은 호출자가 정한 보상에 대한 산술이다(EWC의 "Fisher"는 임베딩 성분 제곱의 평균으로 자체 주석이 근사라고 적는다). 저장소가 3개이고 서로 맞추지 않으며 손상 이력이 주석에 남아 있다.
- **Prime Agent**: "실패에서 배워 후보를 평가하고 퇴보하면 자동으로 되돌린다"는 원본에 없다. refine의 자동 trigger는 "compaction이 방금 성공함"뿐이고, 받아들임은 모델의 판단, 되돌리기는 요청할 때만이다. 회상은 단어 겹침 + IDF다. 옮길 만한 것은 gate 재실행 가드와 적용·되돌리기의 스냅샷 구조였다.
- **Ponytail**: 지침 본문 하나(120줄)와 수준별 필터가 전부이고 나머지는 호스트별 주입 장치다. 자체 측정이 추론 모델(GPT-5.4-mini, GPT-5.5)에서 비용이 26~39% 늘었다고 적는다.

### 옮긴 것

`docs/CONTRACT.md`의 "다른 오픈소스에서 가져와 바꾼 것"에 항목별 출처·바꾼 점·한계가 있다. 요약: 병렬 실행(`alpha-run --parallel`, `Kernel.fork`), 움직인 브랜치 위에 합쳐 재검증 후 반영(`gitx._onto`), 바뀌지 않은 프로젝트에서 실패한 검사 재실행 생략, 학습 묶음 되돌리기(`learn --undo`), `--lean` 지침, 회상의 다양성·coverage floor·유사 중복 차단·주입 패턴.

설계 가치와 부딪혀 바꾼 결정들:

- 병렬은 "프로젝트 폴더 하나에 writer 여럿"이 아니라 "supervisor 하나 아래 스레드 여럿, 프로젝트당 writer 하나"로 넣었다. 커널의 writer 슬롯·fencing·예약이 이미 프로젝트 단위 트랜잭션이어서 규칙을 하나도 풀지 않았다. 스레드를 멈추는 방법은 "충돌과 같은 상태로 남기고 기존 복구에 맡긴다"로 정했다: 새 복구 경로를 만들지 않기 위해서다.
- Ruflo의 통합에는 재검증이 없어서, 깨끗이 합쳐진 결과도 합친 커밋만 꺼낸 사본에서 모든 검사를 다시 통과해야 반영하게 했다.
- Prime의 가드는 git 스냅샷을 쓰는데, Lupus의 프로젝트는 git 저장소가 아닐 수 있어 전체 파일 지문으로 바꿨다.
- Ponytail에서 "게으른 버전을 내고 요청을 되물어라"와 "검사 하나를 남겨라"는 뺐다. 완료 조건은 worker가 협상할 대상이 아니고 검사는 supervisor의 것이다.

- 같은 수정을 한 두 결과를 차례로 반영하면 둘째가 **빈 커밋**을 만들었다. 합친 트리가 브랜치와 같으면 커밋을 만들지 않게 고쳤다.

### 외부 리뷰 (Codex, 3회)

1차 5건, 2차 2건, 3차 "patch is correct". 7건 모두 코드와 대조해 결함으로 확인하고 고쳤으며 각각 회귀 시험이 있다.

1. (P1) 합친 결과가 브랜치와 같을 때 **검사 없이** "반영됨"으로 기록했다. 브랜치에는 다른 변경도 있을 수 있다 → 브랜치 자체를 목표의 검사로 확인한 뒤에만 기록.
2. 중단 신호를 `BEGIN` 전에만 확인해서, 잠금을 기다리는 사이에 중단이 시작되면 그대로 기록됐다 → `BEGIN` 직후와 `COMMIT` 직전에도 확인.
3. 숨은 문자를 가드 **뒤에** 지워서 `i<폭 없는 공백>gnore previous instructions`가 가드를 통과한 뒤 온전한 지시가 됐다 → 지운 뒤에 판정.
4. 검사 자체가 프로젝트 파일을 바꾸는 경우, 바뀐 뒤의 상태에 실패를 묶어 기억했다 → 검사 전후 지문이 같을 때만 기억.
5. 지문이 `.git`·캐시 폴더를 보지 않아, 스테이징 상태에 의존하는 검사가 묵은 실패를 받았다 → git 상태(HEAD, index, refs, config)의 내용 해시와 캐시 폴더 지문을 포함.
6. 4의 경로에서 검사하는 동안 브랜치가 다시 움직이면 알아채지 못했다 → 검사 뒤 HEAD를 다시 확인.
7. worktree의 공유 git 메타데이터(`commondir`의 refs·config)가 지문에 없었다 → 포함.

알고 남긴 것: 프로젝트 밖의 것이나 시간에 의존하는 검사는 같은 supervisor 프로세스 안에서 묵은 실패 때문에 시도 한 번을 잃을 수 있다(완료를 잘못 선언하는 방향은 아니다). 마지막 중단 확인과 `COMMIT` 사이의 아주 짧은 틈.

### 검증

오프라인 시험 366개(3개 건너뜀: 실제 CLI 시험)가 통과한다. 새 시험: 병렬 7(실제로 겹쳐 실행되는지, 같은 프로젝트는 겹치지 않는지, 공유 상한, 단계 상한, 한 스레드 실패 시 정리와 복구, fork의 잠금·중단), 반영 5, 재검사 생략 6, 기억 6, `--lean` 6+1, 학습 되돌리기 1.

### 정직한 위치

세 프로젝트에서 옮길 만한 "동작하는 장점"은 예상보다 적었다. 이름이 큰 기능들(swarm, 합의, 자기 학습, 자동 refine 평가)은 원본에서도 실행부가 없거나 지어낸 값 위의 계산이었다. 실제로 얻은 것은 병렬 실행과 그 결과의 안전한 반영이고(1.16에서 3순위로 남겼던 것), 나머지는 작다. `--lean`과 독립 리뷰는 둘 다 "모델에게 더 말해 주면 결과가 나아진다"는 가정이었고 둘 다 측정에서 확인되지 않았다. "대체 가능한 수준"에 대한 1.16의 평가는 바뀌지 않는다: 숨긴 테스트 기준으로 평범한 호출과 같은 수준이고, Aider·OpenHands와의 직접 비교는 여전히 없다. 측정이 가리키는 다음 일은 그대로 (1) 요청이 기존 테스트와 충돌할 때의 흐름, (2) 요청에 정보가 모자랄 때 구현 전에 되묻는 것이다.
